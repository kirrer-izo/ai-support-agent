One of the most critical design decisions in building the customer support agent was adopting a hybrid, tool-based architecture rather than relying on a monolithic language model. Instead of expecting the model to handle all operations internally, the system delegates specific tasks to specialized, external tools. For instance, the Knowledge Base manages real-time product and policy retrieval, while Gateway tools securely handle transactional data like orders and refunds. Additionally, the Code Interpreter performs complex loyalty calculations, the Browser supports live web research, and AgentCore Memory maintains persistent customer context across sessions. This decoupled approach significantly improves system reliability and accuracy. By offloading computational and retrieval tasks, the model is no longer forced to invent order statuses, calculate discount percentages mentally, or rely solely on outdated training data.

Despite a solid architectural foundation, deploying the application to the ARM64 AgentCore runtime presented a major engineering challenge. The initial container deployment repeatedly stalled during the CodeBuild provisioning phase without generating useful diagnostic logs. To bypass this, we pivoted to a direct code deployment, avoiding Docker and CodeBuild entirely. However, this introduced a new set of local-to-cloud environment compatibility problems. Because development occurred in a Windows environment, pywin32 was inadvertently included in the dependency resolution, which inherently lacks a Linux ARM64 wheel. Furthermore, the repository's configuration explicitly specified Python 3.14, whereas the deployed AgentCore runtime only supported Python 3.13. This mismatch triggered immediate startup failures via PYENV_VERSION=3.14.

Resolving these deployment blockers required strictly targeting the ARM64 architecture during the dependency resolution phase and aligning the repository's configuration with the runtime's available Python version. Moving forward, utilizing a Linux-based development container or setting up strict cross-platform environment checks will ensure local development parity, allowing us to catch OS-specific dependency issues long before deployment.
